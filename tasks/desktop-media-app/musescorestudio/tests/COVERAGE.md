# MuseScore Studio coverage

Version 1.0.0, reference MuseScore Studio 4.7.6. Exact counts and budgets come from `data/manifest.json` of the frozen record; the working manifest has 51 episodes (10 program, 41 GUI) with 802 checkpoints and 852 scoring points, 45 frontend and 807 backend (757 program checks and 50 independent checks of GUI checkpoints).

| Coverage | Behavior |
| --- | --- |
| Import | Program import of 29 generated MusicXML scores and 4 generated MIDI files into a project, each read back as MusicXML, MIDI, score document (mscx), project archive (mscz), metadata listing and element listing; one direct conversion that differs from the read-back path. The MusicXML fixtures include voices, grace notes, multimeasure rests, voltas, segno and coda, clef, key and tempo changes, slurs and hairpins, chord symbols, a transposing clarinet, lyrics with several verses and melismas |

## How points are checked

- Every check reaches the candidate through the task's black-box runtime, the same code that serves the reference to the model: `convert` (the product command line through `start.sh`), `upload` (input documents), `list_files` and `download` (files the product wrote), `windows` and the input operations (the desktop), and the lifecycle operations `restart` and `reset`. Audio is decoded by the verifier's own FFmpeg. Expected values are recorded from the pinned standard answer, never written by hand.
- Observations are projections of what each format defines, not bytes: layout, identifiers, dates, platform values and software banners are dropped; counts, strings and structures stay exact; floats compare within 0.005. Project archives, PDF, Ogg, MEI and MNX differ byte for byte between two runs of the same product, so they are compared by parsed content (archive entries and score document, page count and page size, decoded audio, parsed MEI, MNX with its identifiers renumbered in order of appearance).
- Audio is compared by its musical content, not its samples: format facts (codec, rate, channels, sample format, bit rate) exactly, length within 0.15 s, the first sound within 0.2 s, and for every note run of the recording its pitch classes heard in 70% of its frames and at its onset, one of its pitches in the recorded octave, and its loudest frame within 10 dB of the recorded level. A different synthesizer that plays the right notes at the right times passes; a wrong note, a shifted octave, a faster tempo, a missing part or silence fails.
- PNG trimming is scored as the growth of the image between margin 0 and margins 5 and 10, so it does not depend on the exact pixel size of the engraving.
- Each program scenario prepares its own state in setup items placed right before its first checkpoint (the import and read-back scenarios); the other scenarios are self-contained. A step whose earlier step could not run is blocked, not failed.
- Points that only verify a rejection count together (`requires`) with a positive point of the same episode: refused command lines with a successful metadata listing, refused jobs with a working job, refused transposition options with a working transposition. A frontend point that an inert dialog could satisfy counts with the check of the file the goal wrote.
- An observation that two points would share is scored once: each transposition matrix owns its base fixture, direct conversions that equal the read-back path are left out, the default MP3 bitrate is not scored twice, refused transposition option sets that the product rejects for the same reason keep one point per reason, and the window title of a saved project is checked only in the episodes about saving and reopening.

## GUI episodes

MuseScore Studio has no scripting channel, and its menus, buttons and score canvas are not in the accessibility snapshot (only its windows and file dialogs are). Every GUI episode is therefore native: its first checkpoint opens a score through the Open dialog, the recent scores or the New score dialog and carries its own edit, so no point only repeats the opening of a score. Frontend acceptance conditions name only what a screenshot shows (window title, tab name, status bar text, notes and signs on the staff, dialog content). Program checks read the project or exported file the goal wrote. Input documents are uploaded before the first checkpoint; requested outputs are typed by absolute path in the save and export dialogs.

## Interface and budgets

The evaluator operates the desktop through the runtime's input operations (click, activate, fill, type, press, check, move, drag, scroll, zoom, focus_window, maximize, wait) and observes it through `observe` (windows and file dialogs) and `screenshot` (1440x900, or a magnified rectangle after zoom). Input documents are named by absolute paths in the runtime's input, output and project folders, which the evaluator types in file dialogs (paths outside those folders are refused). GUI budgets scale with the checkpoint count n: calls min(180, 50+30n), seconds min(2400, 600+240n) and tokens 14,000 per call; program episodes run without a model.

`reference/` contains deterministic recipes for the pinned standard only: they drive it through the same runtime operations (keyboard shortcuts and fixed positions of the reference layout, because the product exposes no accessible controls). They are never the candidate's frontend contract.
