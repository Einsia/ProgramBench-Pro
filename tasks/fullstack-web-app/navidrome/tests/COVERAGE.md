## How points are checked

- Every check reaches the candidate through the task's black-box runtime, the same code that serves the reference to the model: its api operation (the native API under /api/, OpenSubsonic under /rest/, sign-in under /auth/, public share addresses under /share/), its library operations (library_put, library_list, library_delete and library_move, which write the music folder the product scans) and its lifecycle operations (restart, status). Nothing reads candidate files, databases or processes.
- Program episodes are the protocol modules, one isolated episode each. Their cases run in declared order on one fresh instance; a scored case is never replayed as setup. A case needs (depends_on) only the scored write that made the state it reads, never a read; a write is bound (requires) to the read that shows its effect. Reads keep only the fields of their own subject, so the other sections of a module do not change them. Scan steps observe only what their change is about, and every library operation runs whatever the product did before.
- The common setup creates the administrator (any success answer; a sign-in supplies the token when the creation answer has none), two ordinary accounts and the scanned fixture library; the scan is awaited until no scan runs and the song total stays unchanged, and a product that settles elsewhere is left as it is for the scored checks to judge.
- Observations normalize generated identities by the field that holds them, whatever their form: ids, the fields that name another object, the object part of cover ids (including the cover of one disc and without the version suffix), the song a play queue stands at and the resources of a share. They become a typed bijection that must stay consistent across the episode (album and artist ids derive from content, song, playlist, user, radio and player ids are random). Wall-clock values keep only whether they are set (absent, null, empty and zero times are unset), durations are whole seconds, bit rates keep their type, secrets and this run's origin are masked, JSON documents in text fields (scrobble filters, embedded lyrics) compare as documents. Response objects may carry extra fields; every reference field must be present and equal unless the reference leaves it empty or unset. Collections whose order the product does not fix (search results, extensions, similar songs, random songs) are compared as sets.
- Pictures are compared by which fixture picture they are; a picture the product draws itself (placeholders, avatars) only has to be an image that is none of them, and a resized picture is compared by its size. Audio and archives are compared by the library files they contain.
- The folder and file totals of a library and the folder count of the scan status follow counting rules of their own; they are checked once and left out of every other observation.
- A point that a server without the feature passes (an empty list, a denial, a missing resource) is bound (requires) to a positive point of the same operation and episode; the refusals of one authentication layer are merged into a few points that each make the refused request and the same request with valid credentials. Frontend points that only verify an empty view or a refusal are bound to the positive point of the same feature in their episode.
- The product scans the music folder only on request (periodic and watcher scans are off). A fresh instance runs one scan of its own shortly after it starts; the checks wait for it, and album covers, artist images, rule playlists and play counts, which the product updates in the background, are read until they settle.

## Interface and budgets

The evaluator operates the pages through the runtime's browser operations (open, reload, back, click, fill, type, select, check, press, pointer, drag, wheel, scroll, upload, wait) in a 1280x900 Chromium session that starts at `/app/`, and observes them through the runtime's snapshot (text, controls with refs, form names and bounds) and viewport screenshot; the music folder appears as `/music` in pages, answers and snapshots. Product HTTP interfaces and static assets do not open as pages. GUI episodes use the budget formula scaled by checkpoint count n: calls min(160, 45 + 25n), active seconds min(1800, 480 + 180n), tokens min(1,500,000, 350,000 + 180,000n); browse-albums, song-search and playlist-lifecycle, whose pages take longer to read, have 1,500, 1,200 and 2,400 active seconds instead. Unscored public setup creates the administrator, two ordinary accounts, the scanned music library and the objects an episode starts from through the product's public interfaces and the runtime's library operations.

`reference/` contains the deterministic recipes for the reference only; they drive it through the same runtime operations, and their control names and routes are never the candidate's frontend contract.

## Not scored

- Transcoding and its settings, and the share option to keep the original format: the image has no ffmpeg. Stream parameters that need a transcoder (time offsets, estimated lengths) answer the plain file and are not checked separately.
- OpenSubsonic endpoints that need a disabled feature: jukeboxControl (jukebox off), findSonicPath and getSonicSimilarTracks (plugins off), getTranscodeDecision and getTranscodeStream (no ffmpeg in the image).
- Plugins, external metadata and scrobbling services, the Jellyfin API, Prometheus metrics, insights, podcasts; artist biographies and similar artists (they come only from external services).
- Reference answers that are HTTP 500 and cannot be told from a crashed candidate: deleting or moving library 1, a non-numeric library id, a reversed range (_start greater than _end), removing a missing file as an ordinary account.
- Uploading an m3u playlist through the native API: the reference resolves the listed files against deployment paths the runtime does not expose, so the imported playlist stays empty.
- Reference quirks left unchecked: a partial user update clears the fields it leaves out, creating a user without password or name succeeds, the last administrator can be deleted, an ordinary account may upload artist images.
- OpenSubsonic endpoints that answer 501 or 410: only the HTTP status is compared.
- getOpenSubsonicExtensions answers without credentials in the reference, so it is not part of the denial checks.
- OpenSubsonic request quirks left unchecked: the protocol version value is not validated (only its presence is required) and an api key without a user name is refused with a missing-parameter error.
- Filters the reference ignores (the q filter of tags and genres, the genre and library filters of artists) are not checked; getGenres ignores the music folder filter and is checked once.
- Artist cover and image url fields: they depend on the timing of background artwork resolution and are not compared.
- Browser features whose result is visual or passes faster than the evaluator observes: themes and the other personal display settings, drag-and-drop reordering of playlists and of the play queue, seeking, volume and skipping in the web player (songs of the fixture last one or two seconds), the activity and scan progress panels and notifications.
